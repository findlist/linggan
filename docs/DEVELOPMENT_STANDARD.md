# 灵感项目持续开发规范

版本：1.0  
状态：生效  
适用范围：人工开发、定时 Agent、后续子系统和数据流水线

## 1. 开发目标

项目要发展成一个可持续运行的 AI 视频创意平台，完成以下闭环：

```text
趋势发现 → 内容图谱 → 创意生成 → 风险检查 → 自动发布
→ 用户使用 → 数据反馈 → 排序优化 → 下一轮内容生产
```

开发工作的优先级必须服务于完整闭环，不以功能数量、代码行数或页面数量作为进展标准。

北极星指标：每周由平台方案产生并发布的有效视频数。

## 2. 每轮开发的强制读取顺序

每次运行必须先完成以下动作：

1. 阅读根目录 `AGENTS.md`；
2. 完整阅读本规范；
3. 完整阅读 `memory/README.md` 和 `memory/PROGRESS.md`；
4. 阅读 `docs/DEVELOPMENT_PLAN.md` 和与当前阶段有关的章节；
5. 检查 `package.json`、目录结构、Git 状态和现有测试；
6. 用实际代码核实进度文件中的描述，禁止只根据文档假设功能存在。

如果发现上轮记录不准确，应先修正记录，再选择任务。

## 3. 一轮只完成一个可验收目标

每轮开发必须选择一个“最小可交付单元”，满足：

- 有明确用户或系统价值；
- 能在本轮内完成；
- 可以测试或验证；
- 不依赖尚未获得的账号、密钥或外部授权；
- 完成后项目状态比运行前更接近可发布闭环。

可以为完成该目标修改多个相关文件，但不得同时开启多个互不相关的功能。

错误示例：同一轮同时开发登录、采集器、支付和 UI 动画。  
正确示例：完成“趋势记录的数据结构、文件存储实现和对应测试”。

## 4. 任务选择规则

按以下顺序选择本轮任务：

1. P0：构建失败、数据损坏、安全漏洞、现有核心功能不可用；
2. P1：当前里程碑的阻塞任务；
3. P1：`memory/PROGRESS.md` 中标记的“下一轮唯一首选任务”；
4. P2：测试、可观测性、性能、无障碍和技术债；
5. P3：视觉修饰和非关键体验增强。

同优先级中优先选择：依赖最少、验证最清晰、对后续任务解锁最多的事项。

禁止因为任务更有趣而跳过基础设施和阻塞项。

## 5. 动态规划规则

`docs/DEVELOPMENT_PLAN.md` 是方向，不是不可改变的固定清单。每轮允许根据代码现实调整顺序，但必须：

- 不改变产品核心定位；
- 不越过关键依赖；
- 不重复已有能力；
- 在 `memory/PROGRESS.md` 记录调整原因；
- 涉及重大架构、成本或商业策略变化时停止并列为用户决策项。

## 6. 产品边界

首期核心用户是需要稳定产出 AI 短视频的个人创作者和小型内容团队。

核心功能：

- 热点和热梗发现；
- 角色、名场面和热门元素知识库；
- 受约束的创意组合；
- 分镜、提示词、台词和发布文案；
- 自动发布内容方案；
- 收藏、复制、导出和成片反馈；
- 基于真实行为的数据优化。

非当前核心：

- 自建基础视频生成模型；
- 综合社交平台；
- 无授权的影视素材下载站；
- 自动交易、自动搬运或垃圾营销系统。

## 7. 架构原则

### 7.1 模块边界

逐步形成以下边界：

```text
web             前台展示和创作工作台
admin           内容状态、来源和异常管理
api             对外接口与权限边界
collectors      来源适配器，只负责获取和标准化
knowledge       实体、别名、关系和分类
generation      创意组合与制作包生成
ranking         评分、排序和探索策略
publishing      发布状态机和回滚
analytics       行为事件与指标聚合
scheduler       定时任务编排、重试和幂等控制
```

采集、生成和发布不得写成无法独立测试的单个长脚本。

### 7.2 数据优先

- 先定义数据契约，再开发页面和流水线；
- 稳定标识使用不可变 ID，名称变化通过别名处理；
- 所有外部事实记录来源、采集时间和最后验证时间；
- 删除优先使用状态字段，避免直接丢失历史；
- 时间统一保存为 ISO 8601 UTC，展示时转换为 Asia/Shanghai；
- 分数必须保存分项和模型/规则版本，不能只保存总分。

### 7.3 发布状态机

内容至少包含以下状态：

```text
discovered → normalized → generated → safety_passed
→ scheduled → published → updated/archived/failed
```

自动发布不等于跳过安全检查。`blocked` 风险、来源缺失、版权状态未知且使用具体受保护资产、重复度超限的内容不得发布。

发布动作必须幂等：同一候选重复执行不能产生多条相同内容。发布失败必须保存错误和重试次数。

## 8. 内容与版权规范

- 具体动漫、影视、游戏角色可作为 `reference_only` 趋势实体；
- 平台官方生成模板默认转换成原创角色原型；
- 原创、明确授权或公共领域内容才能标记为可商用模板；
- 不下载、托管或重新发布未经授权的影视片段、角色图片和大段台词；
- 不使用真人进行欺骗、色情、诽谤或未授权商业代言；
- 不得通过改写名称掩盖对受保护角色的精确复刻；
- 每条自动发布内容必须保留来源证据和风险判断。

内容规则详见 `docs/CONTENT_SYSTEM.md`。

## 9. 外部采集规范

- 优先使用官方开放 API、RSS、公开榜单和允许访问的网页；
- 遵守来源服务条款、robots 和合理频率；
- 为每个来源配置超时、重试、速率限制和 User-Agent；
- 不绕过登录、验证码、反爬机制和付费墙；
- 不采集私人账号、个人敏感信息和不必要的用户数据；
- 来源不可用时允许降级，但不能生成虚假来源或虚构热度。

新增采集器必须有固定样本测试，避免来源页面变化导致错误数据静默进入内容库。

## 10. 自动决策规范

系统允许自动归一化、评分、生成和发布，但必须满足：

- 每次决策可解释，保存规则版本和输入；
- 权重更新单次变化不超过 10%；
- 样本不足时保持原权重；
- 首页至少保留 15% 探索内容，避免热点单一化；
- 禁止级风险不允许由高热度抵消；
- 自动发布必须有撤回能力和异常熔断；
- 同一来源连续失败时暂停该来源，而不是无限重试。

## 11. 编码规范

- 新增业务代码优先使用 TypeScript；当前原型 JavaScript 在进入 API 阶段时逐步迁移，不做无价值的一次性重写；
- 使用清晰的模块、函数和数据类型，避免隐式全局状态；
- 业务规则与 UI 分离；
- 不在代码中硬编码密钥、线上 URL、账号和个人数据；
- 环境变量必须提供 `.env.example`，真实 `.env` 不提交；
- 错误信息应包含恢复建议，但不得泄露密钥和内部数据；
- 注释解释“为什么”，不复述代码；
- 不引入与当前目标无关的大型依赖；
- 修改公共数据结构时同步迁移、测试和文档。

## 12. UI 与体验规范

- 保持现有深色 Aurora 创意工具风格；
- 页面必须在 375、768、1024 和 1440px 下可用；
- 主要交互触控目标至少 44×44px；
- 键盘可访问，焦点清晰；
- 正文对比度符合 WCAG AA；
- 不用颜色作为唯一状态信号；
- 尊重 `prefers-reduced-motion`；
- 自动发布和生成过程必须显示状态、失败原因和恢复方式。

## 13. 测试与验收

每次修改至少执行与风险相称的验证。

### 基础要求

- 格式和静态语法检查；
- 受影响模块的单元测试；
- `npm run build` 生产构建；
- 关键用户流程的手工或浏览器验证。

### 数据与任务额外要求

- JSON/Schema 校验；
- 幂等性测试；
- 重复执行测试；
- 空数据、坏数据、超时、限流和部分失败测试；
- 使用固定时钟或固定样本保证测试可重复；
- 测试不得访问真实生产账号或产生真实外部发布。

### 完成定义

任务只有同时满足以下条件才能标记完成：

1. 代码或文档实现完整；
2. 验收条件逐项满足；
3. 相关测试通过；
4. 生产构建通过，或明确证明该改动不涉及构建；
5. `memory/PROGRESS.md` 已更新；
6. 没有把失败、TODO 或占位实现描述成已完成。

## 14. Git 与工作区规范

- 开始前查看工作区状态，用户现有改动不得覆盖；
- 只修改当前任务相关文件；
- 禁止 `git reset --hard`、强制推送和批量删除；
- 不提交构建产物、依赖目录、密钥和临时诊断文件；
- 用户已明确授权本项目的人工开发和定时任务在每轮验证通过后提交并推送当前远程分支；
- 每轮只暂存与本轮目标相关的文件，提交前执行 `git diff --check`，不得夹带无关用户改动；
- 推送前获取远程最新状态并安全整合，禁止强制推送；推送失败必须记录真实错误和恢复步骤；
- 工作区已有不相关修改时，绕开并在进度中说明；无法安全绕开时停止。

## 15. 外部副作用和权限

除已授权的本项目 Git 提交与推送外，未经明确授权，Agent 不得：

- 部署到生产环境；
- 发布到第三方平台；
- 创建账号、购买服务或升级套餐；
- 写入真实 API Key；
- 删除线上数据；
- 向用户、客户或群组发送消息。

允许完成安全的本地开发、测试、文档和模拟发布。需要新权限时写入阻塞项，不得自行扩大范围。

## 16. 阻塞处理

以下情况标记为 `BLOCKED`：

- 缺少必须的产品选择；
- 需要账号、密钥、域名、支付或外部授权；
- 现有用户改动与任务直接冲突；
- 外部服务不可用且无安全替代方案；
- 继续操作可能造成数据丢失或不可逆副作用。

阻塞时不得停留在空泛报告。应先完成所有不依赖该阻塞项的安全工作，然后在 `memory/PROGRESS.md` 写明：阻塞原因、已完成排查、用户需要提供什么、解除后从哪里继续。

## 17. 进度记录规范

项目记忆统一存放在 `memory/`。项目只使用 `memory/PROGRESS.md` 作为当前进度真源，每轮必须更新：

- 更新时间和轮次；
- 当前阶段与健康状态；
- 本轮选择及选择理由；
- 实际修改文件；
- 验证命令和结果；
- 关键决策；
- 已知问题与阻塞；
- 按优先级排序的后续队列；
- 下一轮唯一首选任务及其验收条件。

历史记录保留在同一文件的“迭代日志”中；超过 30 轮后可按月份归档至 `memory/archive/`，但当前状态和最近五轮必须保留在主文件。

禁止：

- 只写“优化了项目”；
- 把计划当成完成项；
- 删除未解决的阻塞项；
- 同时声明多个“下一轮首选”；
- 为每轮创建不同格式、无法检索的临时进度文件。

## 18. 每轮标准流程

```text
1. 读取规范和进度
2. 检查代码、工作区和基线健康
3. 核实当前阶段
4. 选择一个最小可交付单元
5. 写明验收条件
6. 实现与小步验证
7. 运行完整相关检查
8. 对照验收条件复盘
9. 更新唯一进度文件
10. 输出简明结果和下一轮首选
```

如果当前任务队列已经完成，Agent 应进行一次有边界的健康扫描，发现真实问题后再开发；不得为了保持运行而制造低价值功能。
