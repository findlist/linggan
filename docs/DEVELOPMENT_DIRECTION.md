# 灵感产品双轨自动化开发计划

版本：1.1
日期：2026-07-29
适用范围：产品双轨开发独立自动化流程

本文档是独立自动化流程的专用开发计划，聚焦「数据闭环」与「页面体验」双轨推进。该自动化从本文的未完成任务中选择下一项，并把真实结果同步到 `memory/PROGRESS.md`。

本文可以细化和重排该自动化自身的产品任务，但不得覆盖 `AGENTS.md`、`docs/DEVELOPMENT_STANDARD.md`、`memory/README.md` 中的安全、数据、测试、记忆和 Git 规则。若产品任务发生冲突，以可验证的端到端价值和依赖顺序决定，不以“页面优先”简单覆盖数据正确性。

---

## 一、为什么要双轨并行

之前的开发重心偏向后端数据管道（采集 → 入库 → 候选生成），用户看到的页面进展滞后。反过来，只做页面不做数据，产品缺乏持续生命力。

**核心原则：数据建设和页面体验持续保持并行，但每轮只交付一个可独立验证、可回滚的垂直切片。切片可以同时触及数据与页面，也可以只完成一个必要前置任务。**

## 二、当前问题诊断

### 2.1 用户视角

| 问题 | 具体表现 | 影响 |
|---|---|---|
| 内容太少 | 6 部作品、10 个角色、6 个名场面，虽然排列组合数量较多，但高质量、低风险组合仍有限 | 用户很快感受到题材和结构重复 |
| 生成结果千篇一律 | 钩子只有 3 个模板，对白靠 hash 拼接 | 多生成几次发现是套公式 |
| 热点雷达是空的 | 3 个频道卡片显示"待入库" | 用户感觉产品没做完 |
| 没有详情页 | 角色/作品/名场面只有列表卡片 | 无法深入了解素材 |
| 收藏很弱 | localStorage 只存标题和钩子 | 换设备丢失，无法管理 |
| 没有导出 | 只能复制纯文本 | 无法导出到其他工具 |
| 没有创作历史 | 每次生成覆盖上一个 | 无法回看和对比 |
| 搜索太简陋 | 只做字符串匹配 | 不能按类型/情绪/版权筛选 |

### 2.2 数据视角

| 问题 | 具体表现 | 影响 |
|---|---|---|
| 候选生成未接通正式趋势库 | 仍读取示例 JSON | 采集到的热点无法进入生成流程 |
| 无固定来源适配器 | 独立采集 Agent 已产生公开批次，但尚无针对稳定结构化来源的可测试连接器 | 来源覆盖与字段稳定性不足 |
| 候选不持久化 | 只输出到标准输出 | 无法管理审核流程 |
| 无发布状态机 | 无 candidates 表写入 | 无法跟踪候选生命周期 |
| 无行为采集 | 无事件记录 | 无法优化排序 |
| 知识库规模小 | 6 部作品结构验证规模 | 创意多样性不足 |

## 三、双轨开发路线

### Phase 1：基础体验 + 本地闭环（第 1—2 周）

本阶段按依赖顺序交付垂直切片，不强制把两个无关任务合并到同一提交。

#### 轨道 A — 数据与后端

| 序号 | 任务 | 优先级 | 验收条件 | 预估 |
|---|---|---|---|---|
| A1 | 候选流水线读取 SQLite 正式趋势 | P0 | 空库回退明确、正常库生成候选、保留示例输入、测试覆盖正常/空库/坏库 | 4h |
| A2 | 正式趋势查询与前端导出边界 | P0 | 从 SQLite 生成经过 Schema 校验的只读 JSON；空库、坏库和原子替换有测试 | 4h |
| A3 | 知识库增量合并与去重命令 | P1 | 支持分批填充、跨批次幂等、别名归一和来源合并 | 4h |
| A4 | 第一个固定公开来源适配器 | P1 | 使用保存的响应样本测试，不依赖测试时访问公网；输出 CollectionBatchSchema | 6h |
| A5 | 候选持久化与审核状态机 | P1 | candidates 表写入、合法状态流转、幂等键、非法流转测试 | 6h |
| A6 | 统一任务运行日志 | P2 | 采集、迁移、生成、导出各环节有结构化运行记录 | 3h |

#### 轨道 B — 页面与体验

| 序号 | 任务 | 优先级 | 验收条件 | 预估 |
|---|---|---|---|---|
| B1 | 分批扩充素材库 | P1 | 每批通过 Schema 和来源校验；阶段目标 30+ 参考角色、15+ 抽象名场面、10+ 原创原型、8+ 风格 | 每批 3—5h |
| B2 | 升级生成引擎：钩子、性格对白、分镜、文案 | P1 | 固定种子质量测试通过；每次包含完整分镜和发布文案 | 6h |
| B3 | 今日推荐流：首页 10+ 创意卡片 | P1 | 只读取持久化候选；不足 10 条时显示真实数量和空状态 | 4h |
| B4 | 内容详情页（角色/作品/名场面） | P1 | 可点击进入详情，有"开始创作"入口 | 6h |
| B5 | 导出与收藏升级 | P1 | Markdown/JSON 导出，收藏可管理 | 3h |
| B6 | 网站热点雷达消费正式趋势导出 | P0 | 页面不直接访问 SQLite；有数据展示来源和时间，空库显示明确状态 | 4h |

#### 建议执行顺序

| 轮次 | 垂直切片 | 交付价值 |
|---|---|---|
| 第 1 轮 | A1 候选流水线读取 SQLite | 接通采集入库与生成的断点 |
| 第 2 轮 | A2 正式趋势查询与 JSON 导出 | 建立 SQLite 到静态网站的安全边界 |
| 第 3 轮 | B6 热点雷达读取正式趋势导出 | 用户看到真实、可追溯热点 |
| 第 4 轮 | A5 候选持久化与状态机 | 为推荐、历史和审核提供事实来源 |
| 第 5 轮 | B3 今日推荐流读取持久化候选 | 首页形成真实内容消费闭环 |
| 第 6 轮 | A3 知识库增量合并命令 | 建立可维护、可回滚的数据扩充入口 |
| 第 7 轮 | B1 首批小规模素材扩充 | 用真实批次验证增量命令并增加组合空间 |
| 第 8 轮 | B2 生成引擎质量升级 | 提升组合结果差异和可制作性 |
| 第 9 轮 | B4 内容详情页 | 增加素材理解和创作入口 |
| 第 10 轮 | B5 导出与收藏升级 | 支持方案沉淀和外部制作 |
| 第 11 轮 | A4 固定公开来源适配器 | 提高结构化来源的稳定性和可测试性 |
| 第 12 轮 | A6 运行日志 | 统一采集、迁移、生成和导出的可观测性 |

**Phase 1 验收里程碑：** 公开来源 → 采集批次 → Schema 与去重 → SQLite → 候选生成与持久化 → 只读导出 → 网站展示形成完整闭环。页面达到阶段素材目标，生成结果含分镜和文案，推荐流和详情页只展示真实存储数据或明确空状态。

## 四、数据扩充策略

素材库可以人工整理，但每条知名作品、角色和名场面仍必须有公开可核验来源、版权状态和最后验证时间。不得为了数量目标编造关系、台词、热度或来源。

### 4.1 作品扩充目标

从 6 部扩充到 15+ 部，覆盖更多媒介和类型：

- 流浪地球（科幻电影）
- 三体（科幻剧集）
- 咒术回战（热血动漫）
- 进击的巨人（黑暗动漫）
- 繁花（都市剧）
- 狂飙（犯罪剧）
- 原神（开放世界游戏）
- 黑神话悟空（动作游戏）

每批最多新增 3 部作品，每部添加 2—3 个角色和 1—2 个抽象名场面。每批独立校验、提交和回滚；知名实体遵循现有 Schema 和 `reference_only` 边界，不保存精确台词、镜头或受保护素材。

### 4.2 原创角色原型

新增 10 个不依赖任何 IP 的原创角色原型：

- 硬核程序员、外卖诗人、电竞奶奶、退役舞者转行主理人、AI 训练师、深夜电台主播、独立侦探、流浪厨师、极限运动摄影师、社区调解员

原创角色原型写入 `data/seed-entities.json` 的 `characters` 集合并标记为 `original`，不写入强制 `reference_only` 的 `knowledge-base.json.known_characters`。商用前仍需检查名称、造型和描述没有实质复刻现有 IP。

### 4.3 风格扩充

从 4 种扩充到 8 种：

- 现有：电影感热血、一本正经的荒诞、国风动画、伪纪录片
- 新增：赛博朋克霓虹、古风水墨写意、Vlog 日常感、悬疑反转

### 4.4 前端已有但未展示的种子数据

`data/seed-entities.json` 中已有热门元素和叙事模板种子数据，但前端完全未展示。需要在前端增加对应展示区域。

## 五、生成引擎升级方案

### 5.1 钩子模板分类

```text
悬念型：所有人以为... / 没人注意到... / 直到最后一秒才...
反差型：还在计算退路，...已经... / 本以为是...结果是...
提问型：如果...会怎样？ / 为什么没人...？
行动型：第一步：... / 直接掀桌。 / 不废话，先干。
```

每种类型至少 4 个模板，总计 16+ 个，按角色性格、场面节奏和目标时长选择。测试使用固定随机种子：同一输入与种子必须得到相同结果；一组预设输入生成 20 条结果时，规范化钩子唯一率不低于 70%。

### 5.2 性格驱动对白

```text
冷酷型 → 短句、判断式、先说最坏结果
热血型 → 长句、承诺式、用行动回应质疑
腹黑型 → 先肯定再转折、礼貌施压
温柔型 → 平静语气给出行动判断、先安定同伴
```

### 5.3 分镜建议

按时长输出镜头清单：

- 15s：3 个镜头（钩子 → 冲突 → 反转）
- 30s：5 个镜头（钩子 → 铺垫 → 冲突 → 转折 → 收尾）
- 60s：8 个镜头（钩子 → 铺垫 → 升级 → 冲突 → 受阻 → 破局 → 收尾 → 彩蛋）

每个镜头包含：时长、画面描述、动作、情绪。

### 5.4 发布文案

每条方案输出：

- 3 个标题候选（不同风格：悬念/直白/反差）
- 1 段 100 字描述
- 3 个话题标签

当前 `main.js` 约 280 行，但同时承担渲染、状态和生成逻辑，职责已经混杂。Phase 2 开始按行为边界渐进式拆分：

## 八、执行节奏

### 每轮垂直切片原则

1. 每轮只选一个可独立验收的目标，优先选择能接通相邻边界的垂直切片；
2. 同一目标可以同时修改数据与页面，但不得为了形式上的“双轨”捆绑无依赖任务；
3. 每轮使用一个单一目的 Git 提交，测试失败时能够整体回滚；
4. 数据与页面按最近 3 轮观察保持平衡，不要求每一轮机械配对；
5. 开始前检查依赖、工作区和并发采集批次，禁止暂存其他自动化产生的文件。

### 与现有规范的关系

- 本文是本独立自动化的专用产品任务队列，可以重排 `docs/DEVELOPMENT_PLAN.md` 中与本流程相关的功能顺序；
- `memory/PROGRESS.md` 仍是全项目当前状态、完成结果和阻塞的唯一真源，本流程每轮必须同步更新；
- `AGENTS.md`、`memory/README.md` 和 `docs/DEVELOPMENT_STANDARD.md` 的安全、验证、并发和提交规则始终优先；
- 本文与实际代码不一致时先修正文档或记录阻塞，不得把计划描述当作已经实现。

### 独立自动化运行规则

1. 每次运行先读取本文与 `memory/PROGRESS.md`，再检查代码、数据库迁移、测试和 Git 状态；
2. “已完成”必须同时满足：代码存在、验收条件通过、结果已记录在 `memory/PROGRESS.md`。仅有文档描述不算完成；
3. 按“建议执行顺序”选择第一个未完成且前置依赖满足的切片；若被外部权限或产品决策阻塞，记录阻塞并选择不依赖该阻塞的最近任务；
4. 表中工时只用于判断相对规模，不是自动化运行时限。单轮无法安全完成时，按接口、实现、测试或页面消费进一步拆分，但不得留下不可运行的中间状态；
5. 热点采集自动化产生的 `data/collection-inbox/` 批次属于并发外部修改，本流程不得编辑、暂存、提交或删除；
6. 每轮完成后更新 `memory/PROGRESS.md`，运行与风险相称的验证，只提交本轮文件并推送；失败必须记录真实错误，禁止声称完成；
7. 不访问受限来源，不编造数据，不部署，不自动发布到第三方，不写入真实密钥。

### 下一轮执行建议

**第 1 轮垂直切片：A1 — 让每日候选流水线读取 SQLite 正式趋势。**

**选择理由：**

- A1 是采集入库与候选生成之间的关键断点；
- 先稳定正式输入和空库语义，后续页面展示、持久化和内容扩充才能基于真实行为验收；
